## 1. 产品概述

### 1.1 一句话定义

ContentOS 将客户资料、品牌事实、月度计划、AI 选题、脚本版本、客户审核、拍摄、发布、表现数据、策略复盘和长期记忆连接成一条可追踪的短视频运营工作流。

### 1.2 产品愿景

帮助本地生活代运营团队把“依赖个人经验和零散文档的内容生产”升级为“有品牌上下文、有历史记忆、有流程约束、有数据反馈的 AI 协同生产”。

### 1.3 核心价值

1. **减少重复输入**：品牌、产品、账号风格和禁用信息只需维护一次，AI 自动带入。
2. **提升脚本生产效率**：用户先选择 AI 生成的完整视频方向，再生成可修改脚本，而非从空白表单开始。
3. **降低事实和重复风险**：系统自动校验动态事实、历史相似内容、过期 Memory 和禁用信息。
4. **保证版本与流程一致**：脚本、成片、审核和状态变化均可追踪，不覆盖历史。
5. **形成运营学习闭环**：表现指标由代码计算，AI 负责解释，人工确认后才沉淀为长期运营规律。

### 1.4 核心产品原则

- **Compute First, LLM Second**：能由代码准确计算的内容，不交给 LLM。
- **AI 生成，人做决策**：AI 提供候选、解释和建议；审批、发布、长期记忆写入必须由人确认。
- **系统承担技术复杂度**：Embedding、历史召回和重复判断在后台运行，不要求普通用户理解技术概念。
- **业务成功后计费**：模型调用成功不等于业务任务成功，只有业务结果持久化后才扣 AI Points。
- **不把首页做成聊天窗口**：首页以任务、账号、计划和下一步行动为核心。
- **历史不可覆盖**：需要审计的脚本、成片、评分、Prompt 和 Memory 使用新增版本或替代关系保存。

## 2. 背景与问题定义

### 2.1 行业背景

本地生活短视频代运营团队通常同时服务多个客户。每个客户可能包含多个品牌、门店和抖音账号，运营团队需要持续完成选题、脚本、审核、拍摄、发布和复盘。

传统工作流经常分散在微信、Excel、Word、网盘和员工个人经验中，导致资料难复用、版本难追踪、内容容易重复、AI 缺乏准确上下文。

### 2.2 目标用户的主要痛点

| 痛点 | 业务表现 | 产品应对 |
| --- | --- | --- |
| 品牌资料重复填写 | 每次生成脚本都重新介绍客户 | 账号主数据、Memory、Context Builder |
| AI 生成结果不稳定 | 编造价格、活动、产品信息 | 动态事实来源检查、Schema 校验、质量门禁 |
| 选题重复 | 同账号长期重复相似话题 | 同账号历史检索、规则评分、Duplicate Judge |
| 脚本版本混乱 | 运营和客户不知道哪版可拍 | 不可变 Script Version、批准版本指针 |
| 流程断裂 | 脚本批准后仍靠人工通知摄影 | Content 状态机、Shoot Checklist |
| 数据复盘主观 | 靠印象判断内容表现 | 服务端指标聚合、AI 解释、人工确认规律 |
| AI 成本不可控 | 调用失败仍可能收费或重复扣点 | Run Trace、Usage、业务成功后扣点、幂等恢复 |
| Prompt 修改无治理 | 一次修改可能影响全部生产任务 | Skill 版本、Bad Case、Diff、Eval、A/B、人工应用 |

### 2.3 产品机会

市场上常见的 AI 写作工具解决“生成一段文案”，但未解决以下问题：

- AI 是否使用了正确且仍有效的品牌事实；
- 生成方向是否与历史内容重复；
- 结果是否符合当前月度计划；
- 哪一版脚本已经被批准；
- 脚本如何进入拍摄、发布和复盘；
- AI 质量如何持续评估和改进。

ContentOS 的差异化是将 AI 能力嵌入确定性业务流程，而不是把产品简化为通用聊天框。

## 3. 产品目标与非目标

### 3.1 MVP 产品目标

| 编号 | 目标 | 成功表现 |
| --- | --- | --- |
| G-01 | 建立统一业务主数据 | 客户、品牌、门店、账号可追溯且具备组织隔离 |
| G-02 | 跑通 AI 脚本生产主路径 | 选择账号 → 生成方向 → 选择 → 生成脚本 → 修改/审核 |
| G-03 | 降低重复和事实错误 | 自动历史检索，过期信息不进入生产 Context |
| G-04 | 跑通内容生产状态链 | 审核、拍摄、成片、发布均通过合法业务事务推进 |
| G-05 | 建立数据复盘闭环 | 程序计算指标，AI 解释，人工确认策略与 Memory |
| G-06 | 建立 AI 可观测与治理能力 | Run、Step、Token、成本、积分、失败、Skill 版本可追踪 |
| G-07 | 无外部 Key 仍可演示 | LLM/Embedding 缺少 Key 时使用明确标识的确定性 Mock/Fallback |

### 3.2 本阶段非目标

以下能力不属于当前 MVP：

- 真实 OAuth、SSO 或企业身份认证；
- 抖音官方 API、自动发布和自动同步 GMV；
- 在线支付；
- AI 视频生成、自动剪辑和数字人；
- 大型视频文件上传与转码；
- 完整 CRM、合同和财务结算系统；
- 面向公网的多实例生产部署；
- 开放式自主 Agent 直接替用户审批、发布或写入长期记忆。

## 4. 用户与角色

### 4.1 用户角色

| 角色 | 核心目标 | 主要操作 | 关键限制 |
| --- | --- | --- | --- |
| Owner | 管理整个组织 | 团队、权限、配置、成本、质量治理 | 拥有全部权限 |
| Admin | 管理组织业务 | 客户资料、团队协作、运营和 AI 配置 | 不执行系统危险操作 |
| Operator | 完成客户内容运营 | 计划、选题、脚本、审核、拍摄协调、发布与复盘 | 只访问被分配客户 |
| Photographer | 完成拍摄任务 | 查看本人排期和已批准脚本、更新 Checklist | 不能修改客户和脚本资料 |
| Editor | 提交成片版本 | 查看本人任务、提交不可变成片版本 | 不获得其他客户或任务权限 |
| Viewer | 查看授权信息 | 只读查看 | 无写权限 |
| 外部客户审核人 | 审核指定交付物 | 通过 Token 查看并批准/退回脚本或成片 | 只能访问 Token 绑定版本 |

### 4.2 角色责任边界

- AI：生成候选、脚本、解释和建议。
- 系统：权限、去重、计算、枚举、状态、配额、事务、追踪。
- 运营：选择方向、修改脚本、协调生产、确认复盘结果。
- 客户：审核指定脚本或成片，不接触内部技术工具。
- 摄影：执行已批准内容，不参与品牌资料和 AI 配置。
- 管理员：处理额度、模型、成本、Skill 和质量治理。

## 5. 核心用户场景

### 5.1 场景 A：运营快速生成一条脚本

**前置条件**：客户、品牌、账号和基础 Memory 已存在；用户有该客户写权限。

**主流程**：

1. 用户从工作台或“脚本生成”进入快捷流程。
2. 选择账号；系统自动加载品牌资料和当前月度计划。
3. 用户选择视频目标，可选择 AI 推荐目标；主题和补充要求可跳过。
4. AI 生成 3 组完整视频方向，每组包含卖点、创意、Hook、结构、时长、拍法和出镜建议。
5. 系统在后台完成历史召回、重复判断和质量检查。
6. 用户选择一组，可在允许范围内调整时长、拍法、出镜人和创意强度。
7. 系统先保存所选内容，再生成 Script V1。
8. 用户复制口播、创建人工 V2 或提交审核。

**异常流程**：

- Planner 失败：不创建候选，不扣 Planner Points，可重新生成。
- 选题已保存但脚本失败：保留选题，只重试脚本，不重复扣 Planner Points。
- 网络响应丢失：先读取服务端已提交记录，避免重复保存或重复扣费。
- 高重复候选：默认不可选择；用户可“换角度”，新版本重新执行去重。

### 5.2 场景 B：月度批量内容策划

1. 用户建立账号月度计划和内容类型配比。
2. 系统计算目标数量、已创建数量和类型缺口。
3. 用户输入计划生成数量、首要目标和可选特殊要求。
4. Planner 生成候选并逐条去重、质检。
5. 用户只选择需要的候选写入 Content。
6. 未选候选不进入正式内容库。

### 5.3 场景 C：客户审核脚本

1. 运营将当前脚本版本提交审核。
2. Content 进入 `WAITING_APPROVAL`，旧活动批准指针清空。
3. 系统生成高熵外部 Token，数据库只保存 Hash 和过期时间。
4. 客户只能查看该 Content 的指定 Script Version。
5. 客户选择批准、要求修改或拒绝。
6. 批准后活动批准版本指向被批准版本；要求修改则回到 `SCRIPTING`。

### 5.4 场景 D：安排与执行拍摄

1. 运营创建 Shoot，选择门店、时间、运营和摄影。
2. 只有 `APPROVED` 且存在活动批准脚本的内容可以加入。
3. 加入时在事务中创建 Shoot Item、更新 Content 状态并写状态日志。
4. 摄影查看标题、Hook、批准脚本、人物、产品和 shots。
5. 摄影标记已拍、缺镜、改期或取消。
6. Shoot 整体状态由关联项计算，不允许人工填写完成数量。

### 5.5 场景 E：发布与数据复盘

1. 通过成片审核的 Content 进入 `READY_TO_PUBLISH`。
2. 运营人工创建 Publish 记录，系统在同一事务中进入 `PUBLISHED`。
3. 运营通过表单或 CSV 录入多个时间点 Performance Snapshot。
4. 服务端计算互动率、团购点击率、订单转化率和千次播放 GMV。
5. AI 只接收聚合事实、Top/Bottom 摘要和相关 Memory。
6. 用户确认复盘或策略后，系统才创建 Performance/Strategy Memory。
7. 用户可创建下月计划草案，但不覆盖既有计划。

- 去重、Embedding、Run、Eval 等技术概念不应出现在客户审核页面。
- 设置入口位于头像菜单，减少主导航噪声。

## 8. AI 系统需求

### 8.1 模型与调用方式

| 模型档位 | 当前配置 | 适用任务 |
| --- | --- | --- |
| Light | `qwen3.8-flash` | 重复判断、轻量质量检查等 |
| Standard | `qwen3.7-plus` | 内容策划、表现分析等 |
| Strong | `qwen3.8-max` | 脚本生成、策略规划等 |

所有调用通过唯一 OpenAI Compatible LLM Client 进入百炼，不允许业务模块直接调用模型端点。

统一 Client 必须：

- 统一连接和整体超时；
- 网络错误或 429/5xx 最多自动重试一次；
- 整体生成超时不重复发起，避免双请求；
- 保存 Provider Request ID、实际模型、Token、耗时和重试次数；
- 统一解析 JSON；
- 不返回 API Key、Base URL、完整环境变量或服务器绝对路径；
- 没有 Key 时进入明确标识的确定性 Mock；
- Live 模式失败时不得自动返回 Mock 结果冒充成功。

### 8.2 Skill 配置

当前内置 Skill：

- `content_planner`
- `script_generator`
- `script_rewriter`
- `duplicate_judge`
- `memory_candidate_extractor`
- `performance_analyzer`
- `strategy_planner`
- `quality_checker`

每个 Skill 保存 Prompt、输入/输出 Schema、模型档位、Point Cost 和当前版本。回滚不得删除历史，而是使用旧内容创建一个新版本。

### 8.3 输出验证

正式 LLM 输出写入业务数据库前必须依次通过：

1. JSON 解析；
2. Skill Output JSON Schema；
3. 业务 Zod Schema；
4. 枚举与引用范围校验；
5. 动态事实与禁用信息检查；
6. 对应业务事务。

任何阶段失败均不得写入正式业务结果。

### 8.4 Run Trace

Run 类型分为：

- `production`：正式业务任务；
- `test`：Skill 或去重测试，不扣正式 Points；
- `eval`：Prompt A/B 与评测，不与生产指标混合。

Run 状态包含：queued、running、completed、completed_with_warnings、manual_review_required、failed、cancelled。

Run Step 必须记录步骤代码、输入/输出安全快照、错误、Warning、时间、耗时和业务结果引用。

### 8.5 AI Points 与成本

- 正式调用前只检查剩余额度，不预先永久扣费。
- 业务结果成功持久化后，在同一事务中写 Consume Ledger 并增加 Used Points。
- 模型调用发生但业务失败时，保存真实 Usage 与成本，`billed_points=0`。
- Test/Eval 默认不扣正式 Points。
- 只有存在生效模型价格配置时才计算 Estimated Cost，否则返回 null。

## 9. Memory 与 Context 需求

### 9.1 Memory 准入原则

长期 Memory 只允许来自：

- 已确认品牌事实；
- 用户明确确认的偏好；
- 有数据支持且经人工确认的表现规律；
- 已确认策略复盘；
- 用户人工新增。

聊天记录、普通 AI 输出和未确认分析不得自动进入长期 Memory。

### 9.2 Memory 替代规则

同一组织、Scope、Scope ID、Memory Key 只能有一个 Active 记录。更新事实时：

1. 创建新 Memory；
2. 将旧记录标记为 Superseded；
3. 新记录指向被替代记录；
4. 全过程在同一事务中完成。

Context 只读取 Active、已生效且未过期的记录。

### 9.3 Context 分层

| 层级 | 内容 | 预算 |
| --- | --- | --- |
| L0 | 系统规则 | 固定规则集 |
| L1 | 品牌/账号稳定资料 | 最多 6 项 |
| L2 | 当前计划和当前任务 | 按当前任务装配 |
| L3 | 相关 Active Memory | 最多 20 条 |
| L4 | 历史内容结构化摘要 | 最多 10 条 |

整体字符估算预算为 12,000。超出时按优先级截断，并保存 Context Snapshot，记录使用的 Memory、Content、Plan、截断原因、字符/Token 估算和构建时间。

## 10. 历史检索与重复判断

### 10.1 历史内容导入

- 支持 CSV、JSON 和手动录入；
- 文件上限 1 MB，单次最多 200 行；
- 必须先预览、字段映射和校验，再正式提交；
- 支持 External ID、标题+发布时间、Canonical 三类去重键；
- 正式提交只接受已持久化且无错误的预览批次。

### 10.2 Embedding

Canonical Text 由代码生成：

```text
title + topic + angle + hook_text + core_message
```

不默认使用完整脚本。字段变化后 Source Hash 变化，旧向量标记为 Stale，再重新生成。

### 10.3 Fallback

没有 Embedding Key 时，使用中文字符 Bigram、关键词权重和同义词归一的确定性相似度。产品核心流程不得因此不可用。

### 10.4 检索和重复判断

- 只召回同一 Organization + Account 下已发布或已复盘内容；
- 保存 Top10 的 Content ID、相似度、方法、Source Hash 和 Rank；
- 规则综合 Topic、Angle、Hook、Core Message 和语义相似度；
- 不能仅因 Topic 相同就判重复；
- 最多 Top5 进入 Duplicate Judge；
- 模型只能引用本次 Top5 Content ID；
- High 默认不可选择，Remixable 可选择但展示相似历史。

## 11. 内容状态机

允许状态：

```text
IDEA
→ SCRIPTING
→ WAITING_APPROVAL
→ APPROVED
→ WAITING_SHOOT
→ SHOT
→ EDITING
→ WAITING_REVIEW
↔ REVISION
→ READY_TO_PUBLISH
→ PUBLISHED
→ REVIEWED
```

特殊回退：

- WAITING_APPROVAL → SCRIPTING：脚本要求修改；
- WAITING_SHOOT → APPROVED：从尚未执行的 Shoot 中移除；
- READY_TO_PUBLISH → WAITING_REVIEW：新成片重新提交审核。

状态规则：

- 不允许任意跳转；
- 通用 Transition API 不得执行需要业务副作用的转换；
- 状态变化和副作用必须在同一事务中；
- 成功转换必须追加 Status Log；
- 看板列可以合并多个底层状态，但拖动仍调用合法状态 API。

### 12.1 核心关系

```text
Organization
├── Users
├── Clients
│   ├── Brands
│   │   ├── Stores
```

Content 继续关联 Script Version、Approval、Shoot Item、Edit Version、Publish、Performance Snapshot、Retrieval 和 Run。

- 同组织但未授权客户返回 403；
- ID 使用 UUID，不使用数组索引。

### 12.3 时间与审计

- 时间以 ISO 8601 保存，展示时本地化；
- 重要版本不直接覆盖；
- 权限变更、状态变化和关键操作保留审计或日志；
- Demo 数据使用 `is_demo` 明确标识。

## 16. 非功能需求

### 16.1 安全

- API Key 仅在服务端环境变量中读取；
- 前端、API 响应和 Run Trace 不得返回 Key、完整环境变量或服务器绝对路径；
- 外部 Token 只保存 Hash，并绑定版本和过期时间；
- 所有权限必须在服务端校验；
- Provider 错误正文不得原样透传，避免回显输入或敏感数据。

### 16.2 可靠性

- 业务写操作尽量使用事务；
- AI 调用和业务持久化分开记录；
- 幂等消费 Ledger 防止同一 Run 重复扣点；
- 保存响应丢失时先查询服务端状态；
- 数据库重启和页面刷新后数据仍保留；
- LLM/Embedding 无 Key 时核心演示链可运行。

### 16.3 性能与限制

- 本地 MVP 使用 SQLite，适合单机演示与中小规模开发验证；
- AI 请求统一设置连接和整体超时；
- Context 严格受预算限制；
- 导入限制为单次 200 行、1 MB；
- 生产化前需评估 PostgreSQL、队列、对象存储和并发控制。

### 16.4 可观测性

- 每个请求有 Request ID；
- 每次 AI 任务有 Run 和 Step；
- 记录模型、Skill Version、Token、成本、Points、错误和重试；
- Run Trace 使用安全清洗后的输入输出快照。

- 编辑流程后端完整，但独立剪辑任务入口已从主导航移除，后续应继续轻量化；
- `/accounts` 独立页面仍保留兼容能力，但品牌与账号的主要入口已经回归客户详情；
- 当前开发身份切换器不等同于真实登录。

### 18.3 已知限制

- 本地 SQLite 不适合直接作为公网多实例生产数据库；
- 无真实抖音发布和数据同步；
- 无视频文件存储、转码和播放器审阅能力；
- 无消息通知、任务队列和异步 Worker；
- 当前 AI 工作流是受控编排，不是开放式自主 Agent；
- 尚无真实客户长期使用数据，因此不能宣称效率提升或转化提升已经被验证。

## 19. 后续路线图建议

### Phase A：生产化基础

1. 接入真实身份认证与组织邀请；
2. SQLite 迁移 PostgreSQL；
3. 增加后台任务队列、重试和断点恢复；
4. 接入对象存储和成片在线预览；
5. 建立生产环境日志、监控和告警。

### Phase B：外部平台连接

1. 通过合规开放接口接入抖音账号授权；
2. 发布记录与平台 Post ID 自动同步；
3. 自动同步表现数据和 GMV；
4. 增加通知与客户审核提醒。

### Phase C：受控 Agent Harness

在现有 Run、Step、权限、Context 和业务服务之上增加受控 Agent 编排层：

- Agent 只能调用注册工具，不直接访问数据库；
- 读取型工具可自动执行；
- 生成型工具只产出草稿；
- 审核、发布、扣费和 Memory 写入必须人工确认；
- 每个工具使用 Zod 输入输出和服务端权限；
- 设置最大步数、时间、Token 预算、Checkpoint 和幂等键；
- 第一版只覆盖“账号 → 选题 → 去重 → 脚本 → 提交审核”。

### Phase D：数据驱动优化

1. 基于真实用户采集漏斗和失败原因；
2. 优化首次审核通过率与脚本可拍摄性；
3. 建立行业模板但保持品牌事实隔离；
4. 扩展可解释的推荐和策略实验；
5. 使用真实 Bad Case 扩充 Eval Set。

## 20. 面试与评审时的核心产品结论

1. ContentOS 不是单点 AI 写作工具，而是 AI 内容生产操作系统。
2. 项目最重要的产品判断，是把 AI、代码和人的责任边界分开。
3. AI 负责非确定性的生成与解释；代码负责权限、计算、状态、事实约束和计费；人负责审批和最终决策。
4. Context、Memory 和历史检索解决“AI不了解客户”的问题，版本与状态机解决“结果无法进入生产”的问题。
5. Run Trace、失败不扣点、Bad Case 和 Prompt A/B 解决“AI不可控、不可解释、不可持续改进”的问题。
6. 当前项目已完成本地 MVP 主链与质量链，但真实登录、平台 API、云数据库和长期线上指标仍属于生产化阶段。
